# Phase 1.1: Service Taxonomy Expansion - Research

**Researched:** 2026-03-11
**Domain:** Data layer refactoring -- expanding TypeScript service definitions from 11 to 16 entries
**Confidence:** HIGH

## Summary

Phase 1.1 is a focused data layer task: split 5 broad service categories into 16 intent-specific services, update all downstream data structures that reference service slugs, and ensure the helper functions generate the correct 240 (15 cities x 16 services) combinations. The technical risk is low since this is straightforward TypeScript data file editing, but the coordination risk is moderate because service slugs are referenced across 4 data files and 1 external project.

The critical constraint is preserving existing specialty page hrefs. The current 11 services have `href` fields pointing to `/specialties/{slug}` pages that exist in the Next.js app. When "fences-gates-decks" splits into multiple services, only ONE of the new services should link to `/specialties/fences-gates-decks` -- the others need new hrefs or null hrefs since their specialty pages do not exist yet.

**Primary recommendation:** Modify `services.ts` to define 16 services, update `case-studies.ts` serviceCategories to use the new slugs, update `keywords.ts` if needed, and update the `helpers.ts` combination count. The `specialties.ts` file must NOT be touched (per CLAUDE.md migration rules).

All `relatedServices` arrays in the current 11 services reference old slugs. These must be updated to reference new slugs. For example, a service that currently lists `'fences-gates-decks'` as a related service should list the most relevant split service instead (e.g., `'redwood-fence-installation'` or `'new-deck-construction'`).

### Anti-Patterns to Avoid

- **Creating new specialty pages:** This phase only touches data files. No new routes or pages.
- **Modifying specialties.ts:** CLAUDE.md explicitly prohibits changes to existing data arrays. `specialties.ts` is the homepage/nav data -- leave it alone.
- **Breaking the external content gen import:** `pseo-content-gen/scripts/` imports from `data/helpers.ts` using relative paths. The function signatures must remain compatible.

## Common Pitfalls

### Pitfall 1: Orphaned Slug References
**What goes wrong:** Old slugs like `'fences-gates-decks'` remain in `relatedServices` or `serviceCategories` arrays after the split, causing silent failures when looking up services by slug.
**Why it happens:** The Service interface doesn't enforce that relatedServices values are valid service slugs at the type level.
**How to avoid:** After updating services.ts, grep the entire `data/` directory for every old slug that was renamed or removed. Verify zero references remain to: `garden-boxes`, `fences-gates-decks`, `hardscape`, `painting` as service slugs.
**Warning signs:** `getCaseStudiesForService('fences-gates-decks')` returns results but the slug no longer exists in SERVICES.

### Pitfall 2: Combination Count Mismatch
**What goes wrong:** `getAllCityServiceParams()` returns wrong count because SERVICES array length changed but tests still expect 165.
**Why it happens:** The old Phase 1 verification scripts hardcoded `165` (15 x 11). Now it should be `240` (15 x 16).
**How to avoid:** Update the helpers.ts JSDoc comment from "165" to "240". Run verification with the new expected count.
**Warning signs:** Content generation script generates wrong number of pages.

### Pitfall 3: Keywords Cannibalization Between Split Services
**What goes wrong:** "redwood-fence-installation in Palo Alto" and "gate-installation-repair in Palo Alto" have overlapping keywords because the keyword generator only uses service.keywords.
**Why it happens:** Split services share parent domain so keywords can overlap.
**How to avoid:** Ensure each new service's `keywords` array is distinct and intent-specific. "fence installation" keywords should NOT appear on the gate service. "deck building" should NOT appear on the fence service.
**Warning signs:** Two PSEO pages for the same city targeting nearly identical search terms.

### Pitfall 4: External Content Gen Script Breaks
**What goes wrong:** The `pseo-content-gen/` project imports from `../../nextjs-cf.design/data/helpers` and fails after the service expansion.
**Why it happens:** The script uses `getAllCityServiceParams()` which will now return 240 instead of 165 combinations. If it has hardcoded limits or expectations, it could fail.
**How to avoid:** Check that `generate-content.ts` has no hardcoded `165` references. The current code looks clean (no hardcoded count), but verify after changes.
**Warning signs:** Content generation script errors or generates wrong number of files.

### Pitfall 5: slug vs href Confusion
**What goes wrong:** New service slug `redwood-fence-installation` is used as an href, creating a broken link to `/specialties/redwood-fence-installation` which does not exist.
**Why it happens:** The `slug` and `href` fields serve different purposes. `slug` is for PSEO routes (`/[city]/[service]/`), `href` is for linking back to the pillar specialty page.
**How to avoid:** Explicitly set `href` for every new service to point to the correct existing specialty page. Never auto-generate href from slug.
**Warning signs:** 404 errors on specialty page links from PSEO pages.

### Verification Script Pattern
```typescript
// Verify all 16 services, 240 combinations, no orphaned slugs
import { SERVICES, SERVICE_BY_SLUG, SERVICE_SLUGS } from './data/services';
import { getAllCityServiceParams } from './data/helpers';
import { CASE_STUDIES } from './data/case-studies';

// Count check
console.assert(SERVICES.length === 16, `Expected 16 services, got ${SERVICES.length}`);
console.assert(getAllCityServiceParams().length === 240, `Expected 240 params`);

// No orphaned relatedServices references
for (const s of SERVICES) {
  for (const rs of s.relatedServices) {
    console.assert(SERVICE_BY_SLUG.has(rs), `Orphan: ${s.slug} references ${rs}`);
  }
}

// No orphaned serviceCategories in case studies
for (const cs of CASE_STUDIES) {
  for (const sc of cs.serviceCategories) {
    console.assert(SERVICE_BY_SLUG.has(sc), `Orphan in case study: ${cs.title} references ${sc}`);
  }
}

// All hrefs point to valid specialty pages
const validHrefs = [
  '/specialties/garden-boxes', '/specialties/tree-shrub-removal',
  '/specialties/shed-renovation', '/specialties/fences-gates-decks',
  '/specialties/custom-carpentry', '/specialties/hardscape',
  '/specialties/painting', '/specialties/squirrel-rat-excluders',
  '/specialties/refinishing', '/specialties/landscape-design',
  '/specialties/demolition-hauling',
];
for (const s of SERVICES) {
  console.assert(validHrefs.includes(s.href), `Invalid href: ${s.slug} -> ${s.href}`);
}
```
